    在上图架构中，[dao] [1] 层通过SGBD 专属的类库进行交互，该类库随 SGBD 一起提供。该层实现了被称为 ADO（Active X Data Objects）的标准功能。此类层被称为提供程序（此处指数据库访问提供程序）或连接器。 如今，大多数 SGBD 都配备了 ADO.NET 连接器，而在 .NET 平台初期并非如此。 .NET连接器未向[dao]层提供标准接口，因此该层代码中包含连接器的类名。 如果更换 SGBD，就意味着更换连接器和类，因此必须修改 [dao] 层。这既是一种高效的架构，因为连接器 .NET 专为某个特定的 SGBD 编写，因此能最大限度地利用该连接器；但同时也具有刚性，因为更换 SGBD 意味着必须更改 [dao] 层。 但这一观点需加以权衡：企业通常不会频繁更换 SGBD。此外，我们稍后将看到，自 .NET 2.0 版本以来，已推出一种通用连接器，它在不牺牲性能的前提下提供了灵活性。

    9.2. 数据源的两种使用模式

    .NET 平台支持通过两种不同方式利用数据源：

    1. 联机模式
    2. 脱机模式

    在联机模式下，应用程序

    1. 会与数据源建立连接
    2. 与数据源进行读写操作
    3. 关闭连接

    在脱机模式下，应用程序

    1. 与数据源建立连接
    2. 获取数据源全部或部分数据的内存副本
    3. 关闭连接
    4. 对数据的内存副本进行读写操作
    5. 工作完成后，建立连接，将修改后的数据发送至数据源以便其更新，然后关闭连接

    本文仅探讨连接模式。

    9.3.2. SQL语言的四个基本命令

    SQL（结构化语言查询）是一种部分标准化的数据库查询和更新语言。 所有 SGBD 都遵循 SQL 的标准化部分，但同时为该语言添加了专有扩展，以利用 SGBD 的某些特殊特性。 我们已经遇到过两个例子：主键的自动生成以及表列的允许类型通常取决于SGBD。

    我们介绍的SQL语言的四个基本命令是标准化的，并被所有SGBD所接受：

    select col1, col2,... 
from table1, table2,...
where condition
order by expression
...
    用于获取数据库中数据的查询语句。仅第一行的关键字为必填项，其余为可选项。此外还有其他未在此列出的关键字。
    1. 系统会将“from”关键字后面的所有表进行连接
    2. 仅保留位于 select 关键字后面的列
    3. 仅保留满足 where 关键字条件的行
    4. 根据 order by 关键字表达式排序后的行即构成查询结果。该结果是一个表。 
    insert into table(col1,col2, ...)
values (val1,val2, ...)
    向表中插入一行。(col1, col2, ...) 指定要初始化为值 (val1, val2, ...) 的列。
    update table
set col1=val1, col2=val2
where condition
    更新满足条件的表行（若无where子句，则更新所有行）。对于这些行，col1列将接收值vali
    delete from table
where condition
    删除所有满足条件的表行

    9.3.3. ADO.NET 连接模式的基础接口

    让我们回到通过 ADO.NET 连接器调用数据库的应用程序架构：

    在连接模式下，该应用程序：

    1. 与数据源建立连接
    2. 对数据源进行读写操作
    3. 关闭连接

    以下三个接口主要涉及这些操作：

    • IDbConnection，封装了连接的属性与方法。
    • IDbCommand，封装已执行的 SQL 命令的属性和方法。
    • IDataReader，封装了 SQL Select 命令结果的属性和方法。

    9.3.7. 执行 SELECT 查询

    执行 SQL 命令需要以下步骤：

    1. 连接数据库
    2. 向数据库发送 SQL 命令
    3. 处理 SQL 命令的结果
    4. 关闭连接

    步骤 2 和 3 会反复执行，而连接关闭仅在数据库处理结束时进行。打开的连接是 SGBD 的有限资源。 必须节约这些资源。因此，应始终设法限制开放连接的存活时间。在所研究的示例中，每次执行 SQL 命令后都会关闭连接。随后为下一个 SQL 命令打开新的连接。连接的打开/关闭操作成本较高。 为降低此成本，某些 SGBD 系统引入了“已建立连接池”的概念：在应用程序初始化时，会建立 N 个连接并分配至该池中。这些连接将保持打开状态直至应用程序结束。 当应用程序建立连接时，它会从池中获取 N 个已建立连接中的一个。当它关闭连接时，该连接会直接放回池中。该系统的优势在于对开发者而言是透明的：无需修改程序即可使用连接池。 连接池的配置取决于 SGBD。

    9.4.6. 该选择哪种连接器？

    让我们回到基于数据库的应用程序架构：

    我们已经了解过多种类型的连接器 ADO.NET：

    • 专有连接器性能最佳，但会使 [dao] 层依赖于专有类。更改 SGBD 意味着需要更改 [dao] 层。
    • ODBC、OLE 或 DB 连接器支持在不更改 [dao] 层的情况下处理多种数据库。其性能低于专有连接器。
    • 通用连接器基于专有连接器构建，同时向 [dao] 层提供标准接口。

    因此，通用连接器似乎是理想的连接器。但在实际应用中，通用连接器无法将 SGBD 的所有特殊性完全隐藏在标准接口背后。 在下一节中，我们将探讨参数化查询的概念。在 SQL Server 中，一个参数化查询的形式如下：

    insert into articles(nom,prix,stockactuel,stockminimum) values(@nom,@prix,@sa,@sm)

    在 MySQL5 中，相同的查询将写为：

    insert into articles(nom,prix,stockactuel,stockminimum) values(?,?,?,?)

    因此，两者在语法上存在差异。第 9.3.3 节中描述的 IDbCommand 接口的参数相关属性如下：

    Parameters
    已配置的 SQL 命令的参数列表。命令 update articles set prix=prix*1.1 where id=@id 包含参数 @id。

    属性 Parameters 的类型为 IDataParameterCollection，即一个接口。它表示命令 SQL CommandText 的所有参数集合。 属性 Parameters 具有方法 Add，用于添加类型为 IDataParameter 的参数，该类型同样是一个接口。该接口具有以下属性：

    • ParameterName：参数名称
    • DbType：参数的类型 SQL
    • Value：参数的赋值
    • ...

    类型 IDataParameter 非常适合 SQL 订单的参数 

    insert into articles(nom,prix,stockactuel,stockminimum) values(@nom,@prix,@sa,@sm)

    ，因为其中包含命名参数。可以使用属性 ParameterName。

    类型 IDataParameter 不适用于订单 SQL 

    insert into articles(nom,prix,stockactuel,stockminimum) values(?,?,?,?)

    因为参数没有命名。此时将根据参数在集合 [IDbCommand.Parameters] 中添加的顺序进行处理。 在此示例中，需按 nom、prix、stockactuel、stockminimum 的顺序插入这 4 个参数。 在带命名参数的请求中，参数添加的顺序并不重要。最终，开发人员在初始化带参数请求的参数时，无法完全忽略其使用的 SGBD。这是通用连接器当前的局限性之一。

    9.6. Transactions

    9.6.1. 概述

    事务是一系列以“原子性”方式执行的 SQL 命令：

    • 要么所有操作都成功
    • 要么其中一项失败，那么之前的所有操作都会被撤销

    最终，事务中的操作要么全部成功应用，要么一个也没应用。当用户自己控制事务时，他可以通过 COMMIT 命令确认事务，或通过 ROLLBACK 命令取消事务。

    在之前的示例中，我们并未使用事务。但实际上存在事务，因为在 SGBD 中，SQL 命令始终在事务内执行。 如果客户 .NET 未自行启动显式事务，则 SGBD 将使用隐式事务。此时通常有两种情况：

    1. 每个单独的 SQL 命令都属于一个事务，该事务由 SGBD 在命令执行前发起，并在命令执行后关闭。 这被称为自动提交模式。因此，整个过程就好像客户端 .NET 为每个 SQL 命令分别执行事务一样。
    2. SGBD 未处于自动提交模式，并在客户 .NET 于事务外发出的第一个订单 SQL 时启动了一个隐式事务，并允许客户关闭该事务。 因此，客户端 .NET 发出的所有 SQL 命令都属于该隐式事务。 该事务可能因各种事件而结束：客户端关闭连接、开始新事务等，但此时便处于依赖 SGBD 的状态。应避免使用此模式。

    默认模式通常由 SGBD 的配置决定。某些 SGBD 默认处于自动提交模式，而其他则不是。SQLServer Compact 默认处于自动提交模式。

    不同用户的 SQL 命令会在并行运行的事务中同时执行。一个事务执行的操作可能会影响另一个事务的操作。不同用户的事务之间有四个隔离级别：

    • 未提交读
    • 已提交读
    • 可重复读
    • 可串行化

    未提交读

    此隔离级别也称为“脏读”。以下是一个在此模式下可能发生的情况示例：

    1. 用户 U1 在表 T 上开始一个事务
    2. 用户 U2 在同一张表 T 上开始一个事务
    3. 用户 U1 修改了表 T 中的行，但尚未提交
    4. 用户 U2 “看到”了这些修改，并根据所见内容做出决策
    5. 用户通过 ROLLBACK 撤销了其事务

    可以看出，在步骤4中，用户U2是基于后来被证明是错误的数据做出的决策。

    已提交读取

    这种隔离级别可以避免上述问题。在此模式下，步骤4中的用户U2将无法“看到”用户U1对表T所做的修改。 只有在 U1 将其事务提交为 COMMIT 之后，他才会看到这些修改。

    在此模式下（也称为“不可重复读”），仍可能遇到以下情况：

    1. 用户 U1 在表 T 上开始一个事务
    2. 用户 U2 在同一张表 T 上开始一个事务
    3. 用户 U2 执行 SELECT 操作，以获取满足特定条件的 T 表行中 C 列的平均值
    4. 用户 U1 修改（UPDATE）表 T 中列 C 的某些值，并提交（COMMIT）
    5. 用户 U2 再次执行与步骤 3 相同的 SELECT 操作。他将发现，由于 U1 所做的修改，C 列的平均值已经发生了变化。

    此时，用户 U2 只能看到由 U1 “提交”的修改。但当他在同一事务中执行时，两个相同的操作（步骤 3 和 5）却产生了不同的结果。 “不可重复读”（Unrepeatable Read）一词正是指这种情况。对于希望获得表 T 稳定快照的人来说，这种情况非常令人困扰。

    可重复读

    在此隔离级别下，只要用户保持在同一事务中，其对数据库的读取结果必然一致。用户操作的是一张“快照”，其他事务（即使已提交）所做的修改永远不会反映到该快照中。 只有当用户自己通过 COMMIT 或 ROLLBACK 结束事务时，才会看到这些修改。

    然而，这种隔离模式尚不完善。在执行上述操作 3 之后，用户 U2 查询的行会被锁定。 在操作4中，用户U1将无法修改（UPDATE）这些行中C列的值。但他可以添加新行（INSERT）。 如果新增的某些行满足步骤3中测试的条件，由于这些新增行的存在，步骤5得出的平均值将与步骤3中得出的不同。这些行有时被称为“幽灵行”。

    为解决这一新问题，需切换至“Serializable”隔离级别。

    Serializable

    在此隔离级别下，事务之间完全相互隔离。它确保两个同时进行的事务的结果，与它们依次执行时得到的结果相同。 为了实现这一结果，在操作4中，当用户U1试图添加会改变用户U1的SELECT操作结果的行时，系统将阻止该操作。 系统将显示一条错误消息，告知其无法插入数据。只有当用户 U2 提交其事务后，该操作才可执行。

    并非所有事务隔离级别都可在所有事务中使用。 默认隔离级别通常为已提交读（Committed Read）。当客户端创建显式事务时，可以显式指定事务所需的隔离级别。

    9.6.2. 事务管理 API

    连接实现了第 9.3.3 节中介绍的 IDbConnection 接口。该接口具有以下方法：

    BeginTransaction
    M
    启动事务。

    该方法有两种签名：

    1. IDbTransaction BeginTransaction()：启动事务并返回用于控制该事务的 IDbTransaction 对象
    2. IDbTransaction BeginTransaction(IsolationLevel level)：进一步指定事务所需的隔离级别。level的取值来自以下枚举： 
    ReadUncommitted
    事务可以读取由其他事务写入但尚未提交的数据——应避免
    ReadCommitted
    事务无法读取其他事务写入但尚未提交的数据。然而，事务中连续两次读取的数据可能会发生变化（不可重复读取），因为其他事务可能在此期间对其进行了修改（读取的行未被锁定——仅更新后的行会被锁定）。 此外，其他事务可能已添加了行（幽灵行），这些行将在第二次读取中被纳入。
    RepeatableRead
    事务读取的行与更新的行一样会被锁定。这可以防止其他事务对其进行修改。但这并不能阻止行被插入。
    Serializable
    事务操作的表会被锁定，从而阻止其他事务插入新行。一切都仿佛该事务是唯一的。这会降低性能，因为事务不再并行处理。
    Snapshot
    事务处理的是在时间点 T 创建的数据副本。当事务为只读时使用。与 serializable 产生相同的结果，同时避免了其开销。

    事务启动后，由类型为 IDbTransaction 的对象进行控制，这是一个接口，我们将使用其以下属性 P 和方法 M：

    名称
    类型
    角色
    Connection

    连接 IDbConnection，该连接支持事务
    Commit
